# Chat About a Photo

A CS3720 Mini Project 1 mobile application for capturing and uploading photos, browsing previous uploads, and sharing chat messages and selected photos in real time.

## Features

- Expo/React Native single-screen app with current shared photo and live chat.
- Camera permission handling, photo capture preview, explicit upload action, and upload status.
- Multipart HTTP upload using the SDK-compatible Expo `File` and `expo/fetch` APIs, an upload gallery, and image serving from FastAPI.
- WebSocket chat and synchronized photo selection, including the latest selection for new connections.
- Bounded WebSocket reconnect retries and visible connection status.

## Architecture

```text
App.js                         Single Expo entry screen and shared app state
components/PhotoSection.js     Camera, preview, upload controls, and gallery
components/ChatSection.js      Message history and chat composer
hooks/useChatWebSocket.js      WebSocket lifecycle, messages, and reconnects
services/api.js                Backend URL, upload, gallery, and image URL validation
backend/main.py                FastAPI HTTP/WebSocket service and /tmp/uploads storage
backend/test_main.py           Backend endpoint and WebSocket tests
render.yaml                    Render Web Service configuration
```

The project uses the traditional `App.js` entry point generated by the blank Expo template. It does not use Expo Router. Current installed versions are in `package.json` and `package-lock.json`; `expo-camera` was installed through `npx expo install` to match the installed Expo SDK.

## Prerequisites

- Node.js/npm compatible with the Expo SDK in `package.json`.
- Python 3.10 or newer (the backend is also compatible with the Python 3.14 environment used during development).
- A phone with Expo Go or an Android emulator. Expo Camera is available in Expo Go on supported devices.

## Local setup

### 1. Start the backend

In PowerShell from the project root:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend\requirements.txt
$env:UPLOAD_DIR = "$PWD\backend\uploads"
Set-Location backend
python -m uvicorn main:app --reload --host 0.0.0.0 --port 8000
```

The service listens on port 8000. `UPLOAD_DIR` is set to an ignored local folder here; Render uses the required `/tmp/uploads` default.

### 2. Configure and start Expo

In a second terminal, from the project root, copy `.env.example` to `.env` and set `EXPO_PUBLIC_BACKEND_URL`:

- **Android emulator:** `http://10.0.2.2:8000`
- **Physical phone:** `http://<your-computer-LAN-IPv4-address>:8000`. Find the computer's Wi-Fi IPv4 address with `ipconfig`; the phone and computer must be on a reachable network, and the computer firewall must allow port 8000.
- **Web on the same computer:** `http://localhost:8000`

For example, replace the placeholder line in `.env` with the appropriate value for your setup. Do not use `localhost` on a physical phone: it points to the phone itself. After changing `.env`, restart Expo so it reloads the public variable.

```powershell
npx expo start --tunnel ngrok --go
```

Scan the displayed QR code with Expo Go. The project includes `@expo/ngrok` so Expo can create a tunnel without logging into an Expo account. Tunnel mode makes the JavaScript development server reachable from the phone; it does **not** tunnel the FastAPI backend. For local backend testing, the phone must still reach the computer's LAN address on port 8000. If that is not possible, deploy the backend and set `EXPO_PUBLIC_BACKEND_URL` to its actual HTTPS service URL. To use LAN mode instead, run `npx expo start --go`.

`EXPO_PUBLIC_BACKEND_URL` is public client configuration, not a secret. Never put credentials or private keys in Expo public environment variables. No production backend URL is included; set it only after deploying your service.

## Backend API

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/` | Service information |
| `GET` | `/health` | Health check, returns `{"status":"ok"}` |
| `POST` | `/upload-photo` | Multipart form upload with the field name `file` |
| `GET` | `/photos` | Uploaded image metadata, newest first |
| `GET` | `/images/{filename}` | Serves an uploaded image |
| WebSocket | `/ws` | Chat and shared-photo updates |

Uploads accept valid JPEG, PNG, or WebP images up to 8 MB and 40 megapixels. The backend generates unique filenames and checks image contents rather than trusting the submitted filename or MIME type. Photo selection messages must reference an existing image on this backend; external URLs are rejected.

The WebSocket accepts messages such as:

```json
{"type":"chat","author":"Device","text":"Hello!","timestamp":"2026-10-26T18:00:00Z"}
{"type":"photo_selected","url":"https://YOUR-BACKEND.onrender.com/images/unique_filename.jpg"}
```

The photo URL in the second example is illustrative only; use the URL returned by your own upload. Chat and photo messages are broadcast to all connected clients, including the sender. A new connection receives the latest selected photo while the backend process remains alive.

## Tests and checks

Run the backend tests from the project root:

```powershell
python -m pytest backend -q
```

Check Expo configuration and bundle the Android app for a local development export:

```powershell
npm run lint
npx expo-doctor

```

The backend test suite covers health/docs, photo upload and static retrieval, invalid image rejection, chat broadcast, photo-selection broadcast and validation, initial selected-photo delivery, and WebSocket disconnect cleanup. A successful local build or automated test does not replace testing camera permission/capture on a physical device or synchronization between two actual clients.

## Render deployment

The included `render.yaml` configures a Python Web Service rooted at `backend`. To deploy without the Blueprint:

1. Push this project to a GitHub or GitLab repository. Create a repository in your own account, then add its remote URL and push your branch; do not use a placeholder repository URL.
2. In Render, choose **New + → Web Service** and connect that repository.
3. Set the service root directory to `backend` (the included Blueprint already does this).
4. Use `pip install -r requirements.txt` as the build command.
5. Use `uvicorn main:app --host 0.0.0.0 --port $PORT` as the start command. Uvicorn requires the `module:application` form (`main:app`); the assignment's abbreviated `uvicorn main ...` form does not identify the FastAPI application.
6. Deploy, then inspect the Render build and runtime logs for import or startup errors.
7. Check `https://<your-service-host>/health`, `/docs`, and `/photos`. After uploading a photo, open the returned `/images/...` URL. Do not substitute an invented Render hostname.
8. Set `EXPO_PUBLIC_BACKEND_URL` in your local Expo `.env` to `https://<your-actual-service-host>`, restart Expo, and test with two clients.

Render's local filesystem is **ephemeral**. The service stores files at `/tmp/uploads` as required, but uploads can disappear after restarts or redeployments. Separate backend instances do not share these files or in-memory WebSocket state. This project intentionally does not add a database or paid object storage.

## CORS and WebSocket notes

The default CORS allowlist includes common local Expo Web development origins. Set `CORS_ALLOW_ORIGINS` to a comma-separated list of browser origins if you deploy a web frontend from another origin. Native mobile clients generally do not send a browser `Origin` header, so browser CORS policy is not the mechanism that secures native uploads or WebSockets. WebSocket and upload validation are implemented separately; this coursework service does not include authentication.

The frontend derives `ws://` for an HTTP backend and `wss://` for HTTPS. Render deployments use secure `wss://` automatically.

## Two-device integration test

1. Start the local backend or deploy it to Render; allow for a Render cold start.
2. Start Expo with the same backend URL configured on both devices/emulators.
3. Confirm both clients show **Live**.
4. Send a chat message on one client and verify it appears on both.
5. Capture and upload a photo on one client and verify both display it.
6. Select an older gallery thumbnail and verify the other client updates without refreshing.
7. If the WebSocket disconnects, verify the client shows its status and reconnects (or use **Reconnect** after the bounded retry limit).

Do not report this as passed until it has actually been performed on two clients.

## Known limitations

- No login, authorization, or persistent chat history is included.
- The gallery metadata is derived from files and held partly in process memory; uploaded files and the latest selection are not shared across independent backend instances.
- Render's `/tmp/uploads` storage is temporary, not permanent.
- Physical-device networking, camera behavior, and two-device synchronization must be tested on the target devices and network.
